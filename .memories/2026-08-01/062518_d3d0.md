## delete-thought-mcp: deployed + connector registered, but tool invocation blocked by Claude Desktop caution

**WHAT:**
- Root-caused the earlier machine hang: gnome-keyring/libsecret D-Bus interaction on XFCE (daemon not in XFCE's autostart `OnlyShowIn`). Fixed by launching `claude-desktop --password-store=basic`, which bypasses the OS keyring entirely — app now starts cleanly. Tradeoff: login session isn't persisted across restarts.
- Confirmed via Supabase dashboard that `delete-thought-mcp` Edge Function is deployed (updated "an hour ago" at check time), alongside the other 5 functions (`open-brain-mcp`, `family-calendar-mcp`, `home-maintenance-mcp`, `household-knowledge-mcp`, `meal-planning-mcp`).
- Registered `delete-thought-mcp` as a new custom connector in Claude Desktop using `?key=<MCP_ACCESS_KEY>` in the URL (not the OAuth Client ID/Secret fields — those don't apply to this key-based auth scheme and were a red herring in the UI).
- Verification attempt via Claude Desktop conversation: captured a throwaway thought, then hit a **UUID discoverability bug** — none of the four core `open-brain-mcp` tools (`capture_thought`, `list_thoughts`, `search_thoughts`, `thought_stats`) ever return a thought's `id` in their tool output, confirmed by reading `server/index.ts` (capture_thought computes `thoughtId` at line 473 but never includes it in the returned confirmation text at line 487-497; `list_thoughts`'s select at line 309 doesn't even fetch `id`; `search_thoughts`'s formatter never emits `t.id`).
- Grabbed the UUID manually from the Supabase Table Editor as a workaround.
- Asked Claude Desktop to call `delete_thought` with that UUID — **it refused**, citing an internal operating-rule against performing irreversible data deletion on the user's behalf, despite explicit user instruction ("delete that thought").
- User deleted the row directly in the Supabase Table Editor instead, bypassing the MCP tool entirely.

**WHY:** Continuing the upstream-adoption thread — deploying and validating `delete-thought-mcp` per the active brief's next steps.

**HOW:** Root-caused via direct inspection (ps/dbus checks on M7GASG5, reading `server/index.ts` and `integrations/delete-thought-mcp/index.ts`) rather than guessing. Noted `delete-thought-mcp`'s tool definition has no `annotations` block (no `destructiveHint`/`readOnlyHint`), unlike the core server's tools — per MCP spec, clients should treat unannotated tools conservatively, which may explain (but doesn't fully confirm) Claude Desktop's refusal.

**IMPACT:**
- Claude Desktop machine-hang issue is resolved (keyring bypass works) — no longer a blocker for future connector work on this machine.
- `delete-thought-mcp` is deployed and connector-registered, but **conversational invocation via Claude Desktop is unconfirmed / actively blocked** — the tool was never successfully executed end-to-end, only manually replicated via direct SQL. Unclear whether this is a soft guardrail (bypassable with more explicit authorization wording) or a hard client-side policy.
- Discovered a real usability gap in the core `open-brain-mcp` server: no tool surfaces a thought's `id`, making any ID-requiring operation (like this delete tool) effectively unreachable through normal conversation without manual DB lookup. Worth fixing upstream (add `id` to `capture_thought` confirmation text, `list_thoughts` output, and `search_thoughts` output) regardless of the refusal issue.
- `integrations/delete-thought-mcp/*` files are still staged/uncommitted on `kae36/personal` — deploy is confirmed, but full working-as-intended status is not, so still holding off commit pending a decision on whether to accept current state or dig further into the refusal / id-surfacing gaps.
