## Fixed Supabase security advisor findings (project `open-brain` / dpcybjkruqrbdlyvfeqb)

Supabase emailed a CRITICAL advisor alert on 03 Aug 2026. Dashboard showed two distinct advisor classes, both traceable to SQL files in this repo.

### Findings

| Advisor | Objects | Source file |
|---|---|---|
| `rls_disabled_in_public` | `crm_persons`, `crm_person_mentions` | `schemas/crm-person-tiers/schema.sql` |
| `security_definer_view` | 5 × `ops_*` (list was cut off in screenshot) | `recipes/brain-health-monitoring/ops-views.sql` |

**Key discovery:** NO view anywhere in this repo set `security_invoker`. Postgres 15+ defaults views to `security_invoker = false`, so views run as their OWNER (`postgres`), which bypasses RLS. `lint-sweep/views.sql` (7 views) and `thought-audit/author-session-id.sql` (`thought_provenance`) have the identical defect and were almost certainly also flagged below the fold.

### Fix approach

Chose **enable RLS with zero policies** for the CRM tables rather than writing SELECT policies. Deny-all for `anon`/`authenticated`; `service_role` bypasses RLS, so the intended access path (server-side service_role client calling `crm_person_tiers()`) is unchanged. This matches the design intent already documented in that file's GRANTS section.

Added `REVOKE ALL ... FROM anon, authenticated` as defense in depth so data stays unreachable even if RLS is later disabled.

### Files changed

- `schemas/crm-person-tiers/schema.sql` — new section 4 (ROW LEVEL SECURITY), renumbered RPC 4→5 and GRANTS 5→6, added REVOKE
- `recipes/brain-health-monitoring/ops-views.sql` — `WITH (security_invoker = true)` on all 8 views + header rationale
- `recipes/lint-sweep/views.sql` — same on all 7 views + header rationale
- `schemas/thought-audit/author-session-id.sql` — same on `thought_provenance`

All source files are idempotent (`CREATE OR REPLACE` / `IF NOT EXISTS`), so re-running them also repairs the live DB.

### Live-DB remediation (scratchpad, NOT committed)

- `fix-advisors.sql` — minimal `ALTER`-only fix; `to_regclass`-guarded loop over all 16 view names, plus a Part 3 that reports any remaining security-definer view the script didn't name
- `check-exposure.sql` — read-only pre-check: whether `anon`/`authenticated` actually held grants on the CRM tables (RLS-off alone is NOT sufficient for public read — PostgREST also needs a table GRANT), current RLS state, per-view invoker status, and whether `thoughts` has RLS at all
