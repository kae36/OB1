## Closed live anon-key exposure on Supabase `open-brain`

The 03 Aug advisor email was **real exposure**, not a static-analysis warning. My initial assessment was wrong and got corrected by evidence.

### What the exposure check actually found

- `anon` AND `authenticated` held full CRUD — **including TRUNCATE** — on `crm_persons` and `crm_person_mentions`, with RLS **off** on both. The anon key is public by design, so these were world-writable.
- All 5 `ops_*` views: owned by `postgres`, `security_invoker=false`, **granted to anon**. Meanwhile `thoughts` has RLS with 1 policy — so `ops_recent_thoughts` / `ops_enrichment_gaps` were serving 180-char content previews of thoughts straight through that policy.
- `lint_*` and `thought_provenance` are **not installed** in this DB — those repo edits are preventive only.

### Root cause

Grants came from schema-level DEFAULT PRIVILEGES, **not** from any repo SQL file. That is why `schemas/crm-person-tiers/schema.sql` granting only to `service_role` was misleading — I reasoned from the file and got it wrong. Saved to memory as `project-supabase-default-privileges`.

### Two bugs in my own remediation, both caught by running it

1. Multi-statement scripts: the Supabase SQL editor returns **only the last statement's result set**. First `check-exposure.sql` silently discarded checks 1-3. Fixed by making it a single UNION ALL query.
2. `ALTER DEFAULT PRIVILEGES FOR ROLE supabase_admin` → `42501 permission denied`; the editor runs as `postgres`, which is not a member of that role. The error **rolled back the whole transaction**, so nothing applied on that run. Fixed by discovering roles from `pg_default_acl`, guarding with `pg_has_role`, and catching `insufficient_privilege` per-role.

### Result after successful run

- `crm_*` tables and all `ops_*` views no longer appear in the anon-reachable audit at all.
- No table in `public` has RLS off.
- `postgres` default privileges tightened; `supabase_admin` unchangeable as `postgres` (accepted — user's own tables are created as `postgres`).

### Open risk, NOT yet resolved

11 tables still grant anon/authenticated full CRUD incl. TRUNCATE — `thoughts`, `activities`, `family_members`, `household_items`, `household_vendors`, `important_dates`, `maintenance_logs`, `maintenance_tasks`, `meal_plans`, `recipes`, `shopping_lists`. They are protected *only* by policy text. RLS with `USING (true)` satisfies the advisor while permitting everything, so the advisor going quiet proves nothing. `policy-audit.sql` written to dump actual `qual`/`with_check` expressions; awaiting results.
