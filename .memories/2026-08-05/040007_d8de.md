## Supabase exposure fully remediated — final state verified

Closing checkpoint for the 03 Aug 2026 advisor incident on `open-brain` (dpcybjkruqrbdlyvfeqb).

### Final verified state

`harden-grants.sql` audit returns 10 rows, all `ok - all privileges are RLS-filtered`:

- `anon` holds **nothing** on any table in `public`.
- `thoughts` is `service_role` only — no anon, no authenticated.
- No `TRUNCATE` / `MAINTAIN` held by any public-API role anywhere.
- 10 extension tables keep exactly SELECT/INSERT/UPDATE/DELETE for `authenticated`, scoped by `auth.uid() = user_id`.
- `crm_*` tables and `ops_*` views absent from the anon-reachable set entirely.

### Key technical findings from the policy audit

- **`thoughts` was never directly exposed.** Its single policy is `USING (auth.role() = 'service_role')`, so anon got zero rows. The leak was exclusively via the security-definer `ops_*` views, which bypassed it.
- **Extension tables were never anon-readable** either: `auth.uid()` is NULL for anon, and `NULL = user_id` is NULL, never TRUE.
- **RLS does not cover TRUNCATE or MAINTAIN.** anon held both on all 11 tables. Not reachable through PostgREST (it exposes no TRUNCATE verb), so latent rather than live — but policies structurally could not have stopped it. This was the real residual and is now revoked.

### Remediation sequence that worked

1. `fix-exposure.sql` — RLS + REVOKE on crm tables; `security_invoker=on` + REVOKE on ops views; default privileges tightened for `postgres`.
2. `harden-grants.sql` — least-privilege pass stripping TRUNCATE/MAINTAIN and removing anon from the 11 remaining tables.

### Accepted / not done

- `supabase_admin` default privileges still grant to anon; unchangeable as `postgres` from the SQL editor. Accepted — user's own tables are created as `postgres`, whose defaults are fixed.
- **Duplicate policies on 7 tables** (`household_items`, `household_vendors`, `maintenance_logs`, `maintenance_tasks`, `meal_plans`, `recipes`, `shopping_lists`) — two identically-defined policies each, from two schema files creating the same rule under different names. Permissive policies OR together so behaviour is unchanged. Cleanup offered, not done.
- **`household_member` JWT policies are likely dead code** — `(auth.jwt() ->> 'role') = 'household_member'` requires a Postgres role of that name for PostgREST to switch into. Reads like working shared-household access but probably never matches. Flagged, unverified.
- API Gateway logs never checked for evidence of actual access during the exposure window; free-tier retention is short so this is likely now unrecoverable.

### Still open

Fork PR #1 (`kae36/OB1`, base `kae36/personal`) is **unmerged**. It carries the source-side fix so re-running the schema files cannot regress the database. CI does not run on it — every workflow is filtered to `branches: [main]` and the fork's default branch is `kae36/personal`.
