## The 09-13 SECURITY DEFINER fix was incomplete; anon exposure was live until 2026-09-19

**WHAT**
- `brain_stats_aggregate` and `get_thought_connections` (both SECURITY DEFINER, bypass RLS on `thoughts`) remained executable by `anon` from 2026-09-13 until now, so anyone with the public anon key could pass `p_exclude_restricted = false` and read restricted-tier stats and content previews.
- Fixed with `.planning/supabase-security/fix-definer-public-grant-2026-09-19.sql`: `REVOKE ALL ... FROM PUBLIC, anon, authenticated` then `GRANT EXECUTE ... TO service_role` on both.
- Verified live by the user: `anon_can_execute = false`, `authenticated_can_execute = false`, `service_role_can_execute = true`, `proacl = {postgres=X/postgres,service_role=X/postgres}` on both functions.

**WHY it was missed**
- Postgres grants EXECUTE on new functions to PUBLIC and `anon` inherits it. The 09-13 fix revoked only from `anon, authenticated`, so PUBLIC's grant survived.
- The 09-13 verification joined `aclexplode(proacl)` to `pg_roles`. PUBLIC is grantee `0` with no `pg_roles` row, so the inner join silently dropped it and the result looked clean.

**HOW found**
- Today's check used `has_function_privilege('anon', oid, 'EXECUTE')`, which counts inherited PUBLIC access, and disagreed with the 09-13 result. Cause inferred from the SQL and confirmed by the post-fix `proacl`; the pre-fix `proacl` was never captured.

**IMPACT**
- Correction to the 2026-09-13 records: "verified live" for this finding was wrong. The catalog has a CORRECTION note; the brief is updated.
- RULE going forward: revoke from `PUBLIC, anon, authenticated`; verify with `has_function_privilege()` and raw `proacl::text`, never a `pg_roles` join. Repo schema files whose REVOKE names only `anon` have the same gap.
- No evidence either way of whether anyone exercised the exposure; there is no access log for it.
