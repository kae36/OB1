## Self-inflicted regression: search_path hardening broke semantic search, found and fixed same session

**WHAT:** Earlier today's `function_search_path_mutable` advisor fix (`fix-lint-findings-2026-09-13.sql`) pinned 6 functions' `search_path` to `public, pg_temp`. Five were unaffected (3 trigger functions touch no extension types; `search_thoughts_text` uses only `pg_catalog`-resolvable tsvector/ts_rank; `upsert_thought` uses only `pg_catalog` sha256). The sixth, `match_thoughts`, calls pgvector's `<=>` operator on the `vector` type -- both of which live in this Supabase project's `extensions` schema, not `public`. Excluding `extensions` from the pinned search_path broke operator resolution, live.

**WHY this matters:** This means semantic search (`search_thoughts`/the ChatGPT-compat `search` tool) was silently broken for some window of time between running that earlier fix and this correction -- discovered only because a semantic search happened to be attempted (as part of demonstrating the new home-task capture workflow), not because anything alerted on it. Full-text search and thought capture were unaffected throughout.

**HOW found and fixed:** The error message itself (`operator does not exist: extensions.vector <=> extensions.vector`) was the direct clue -- named the exact schema. Wrote `fix-match-thoughts-search-path-2026-09-13.sql` adding `extensions` back to just this one function's search_path, with a verification query that independently confirms `pg_extension.extnamespace` for `vector` rather than assuming the `extensions` schema guess was correct. User ran it; verification CSV confirmed both the corrected search_path and the actual extension schema match. Re-ran the original failing semantic search afterward -- succeeded, correctly retrieved the newly-captured thought.

**LESSON for future search_path hardening on this project:** Supabase installs dashboard-toggled extensions (pgvector included) into an `extensions` schema, not `public`. Any function using an extension-provided type or operator (vector, pg_trgm, etc.) needs `extensions` explicitly in its pinned search_path, not just `public, pg_temp`. Worth checking `pg_extension.extnamespace` before pinning search_path on any function that touches extension objects, rather than assuming `public` is sufficient.

**IMPACT:** Semantic search restored and verified live. No other function from today's fixes touches extension-provided types, so this was an isolated, now-closed issue -- not a broader pattern across the other changes made this session.
